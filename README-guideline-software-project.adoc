This guideline is written primarily for AI agents that work in software project repositories. It applies from the creation of a repository through everyday coding and the remake of an existing repository.

[[goal]]
== Goal

. [[governed-repository,a governed repository]]A _governed repository_ is a software project repository in which AI agents write all code without manual programming and changes merge without human review. Human review therefore catches none of its defects.
. The xref:#governed-repository[governed repository] aims to create confidence without human code review. It automatically rejects every change that violates a rule.
. Hard, explicit rules describe the exact state that a xref:#governed-repository[governed repository] must preserve. The governed repository enforces that state automatically.
. Every rule of this guideline serves the goal. A stronger rule replaces a weaker rule. A missing rule that would serve the goal is a gap. A rule that doesn't serve the goal doesn't belong. An improvement to this guideline is judged against the same goal.

[[application]]
== Application

. Every rule of this guideline describes the state of a compliant xref:#governed-repository[governed repository] - its layout, its xref:#harness[harness of automated checks], its code, its tests, its dependencies, and its commit history.
. A rule is satisfied when an inspection confirms that the xref:#governed-repository[governed repository] has the state that the rule describes.
. An AI agent applies the guideline by taking it together with an assignment. Example assignments include:
.. creating a new software project repository on a chosen technology stack whose state follows these rules,
.. remaking an existing software project repository until its state follows these rules,
.. changing a xref:#governed-repository[governed repository] while preserving its compliance.

[[governing-principles]]
== Governing Principles

. The rules apply to every programming language and platform, so they name no concrete tools and no concrete programming languages.
. A rule is absolute: it binds in every case unless the rule itself states its exception.
. A rule that automation can verify reliably is wired into an automated xref:#check[check], and the xref:#governed-repository[governed repository] binds that check to a concrete tool of its technology stack.
. A rule that no xref:#check[automated check] can verify reliably binds with the same force: an xref:#instruction-file[instruction file for AI agents] states it, and an inspection of the xref:#governed-repository[governed repository] against the rule's wording decides compliance.

[[foundations]]
== Foundations

This section defines the terms the guideline uses and states the qualities required of every automated xref:#check[check].

[[definitions]]
=== Definitions

. [[check]]A _check_ is an automated verification with exactly two verdicts: pass and fail. Any outcome other than a pass, including the failure of the check itself to run, is a fail. A warning severity doesn't exist in a xref:#governed-repository[governed repository].
. [[harness]]A _harness_ is the complete set of xref:#check[checks] of a xref:#governed-repository[governed repository].
. [[verification-command,the verification command]]A _verification command_ is a command of the xref:#governed-repository[governed repository] that runs every xref:#check[check] in a fixed order and fails when any check fails. The verdict of the verification command is the verdict of the whole xref:#harness[harness].
. [[file-role,a file role]]A _file role_ is a category that a xref:#governed-repository[governed repository] can determine from a file itself and uses to include or exclude the file from xref:#check[checks].

[[check-qualities]]
=== Check Qualities

. The xref:#check[checks] run at the strictest settings their tools offer, relaxed only where a rule of this guideline declares a cap, a floor, an allowlist, or a xref:#suppressions[machine-readable suppression].
. A xref:#check[check] is deterministic: on the same state of the xref:#governed-repository[governed repository] it reaches the same verdict on every run and on every machine. The exceptions are the two checks of the section xref:#dependencies[] that read a public package registry by design: the xref:#dependency-freshness[freshness check] and the xref:#dependency-vulnerabilities[vulnerability check].
. The toolchain that the xref:#check[checks] run - every analyzer, every build plugin, and every container image - is pinned to an exact version. An upstream release therefore can't change a verdict while the xref:#governed-repository[governed repository] doesn't change.

[[the-verification-command]]
== The Verification Command

. The xref:#governed-repository[governed repository] defines a xref:#verification-command[verification command] and may define commands that run declared subsets of the xref:#check[checks] - for example, a fast command for everyday work.
. The xref:#verification-command[verification command] runs to a verdict on a fresh clone of the xref:#governed-repository[governed repository]. The only preparation a fresh clone needs is installing the toolchain.
. A run of the xref:#verification-command[verification command] doesn't write to the tracked tree of the xref:#governed-repository[governed repository]. A tool that reshapes a source file, such as a formatter or an import sorter, runs as a xref:#check[check] that fails when the tool would change a file and applies the change only through a separate command the governed repository declares. A check compares the tree after a run against the tree before it and fails on any difference, so a pass describes the committed tree and not a tree the run reshaped.
. The xref:#verification-command[verification command] itself starts every external service the tests use.
. The head commit of the main branch passes the xref:#verification-command[verification command].
. A xref:#check[check] the xref:#governed-repository[governed repository] implements itself, rather than one it binds to a third-party tool, is source code of the governed repository. The check meets every rule of the sections xref:#code-rules[] and xref:#testing[], and the xref:#harness[harness] treats it like any other source code.

[[harness-integrity]]
== Harness Integrity

The xref:#harness[harness] stays beyond the xref:#governed-repository[governed repository's] reach. A xref:#check[check] the governed repository can turn off isn't a rule.

. The xref:#harness[harness] decides which xref:#check[checks] run, how strict they must be, and what they exclude. The harness configuration lives outside the xref:#governed-repository[governed repository], or in a xref:#generated-files[generated file] that the regeneration check binds. The governed repository sets only what the harness leaves open.
. The xref:#harness[harness] rejects any setting of the xref:#governed-repository[governed repository] that skips a xref:#check[check], lowers its severity, narrows its scope, or swaps the configuration it reads. Exceptions come only from the harness: a xref:#suppressions[suppression], an exclusion by xref:#file-role[file role], or a stricter cap.
. The xref:#verification-command[verification command] fails on any finding. A report-only mode helps a software project repository adopt the harness. No run in that mode is a pass.

[[governed-repository-organization]]
== Governed Repository Organization

This section describes the layout of a xref:#governed-repository[governed repository], from the xref:#instruction-file[instruction files] to the configuration that fixes formatting.

[[instruction-files]]
=== Instruction Files

. [[instruction-file,an instruction file]]An _instruction file_ is a committed file that holds rules of the xref:#governed-repository[governed repository] for AI agents. [[root-instruction-file,the root instruction file]]The root instruction file is `AGENTS.md` at the top of the governed repository and is neutral to the tools used by AI agents.
. If this guideline and an xref:#instruction-file[instruction file] conflict, this guideline applies. An instruction file adds only details specific to the xref:#governed-repository[governed repository] or one of its directories and doesn't restate this guideline.
. A tool-specific xref:#instruction-file[instruction file] contains only a reference to `AGENTS.md`. A xref:#check[check] rejects any other content and any instruction reference, command, or path that doesn't resolve.

[[production-imports]]
=== Production Imports

Production code imports neither test code nor development-only dependencies. A xref:#check[check] walks every import of production code and fails on either kind.

[[generated-files]]
=== Generated Files

. No generated file carries a direct hand edit: a generated file changes only as the output of its declared generator. The xref:#governed-repository[governed repository] denies AI agents write access to generated files where the runtime used by AI agents supports the denial.
. A xref:#check[check] reruns the declared generator and fails when the generated file differs from the output.
. The xref:#governed-repository[governed repository] excludes generated files, identified by xref:#file-role[file role], from the xref:#check[checks] of the section xref:#code-rules[].

[[governed-repository-configuration]]
=== Governed Repository Configuration

. Line endings, character encoding, indentation, and whitespace handling are fixed by configuration files committed to the xref:#governed-repository[governed repository]. A xref:#check[check] verifies every tracked file that the governed repository doesn't exclude by xref:#file-role[file role], such as binary assets, against that configuration and fails on the first deviation.
. Where the programming language or platform provides a code formatter, the formatter is one of the xref:#check[checks], run under a committed configuration. The check formats every source file not exempt by xref:#file-role[file role] and fails when the output differs from the committed copy.
. No secret sits in any commit. A xref:#check[check] scans the tracked content and the commit history for credentials, keys, and tokens.
. The xref:#governed-repository[governed repository] lists every fake credential committed as a test fixture in a declared secret allowlist. The secret xref:#check[check] fails on any finding outside the secret allowlist.

[[code-rules]]
== Code Rules

This section describes the state of the source code: its size, its types, its names, and the constructs banned from it.

[[size-and-complexity-caps]]
=== Size and Complexity Caps

. Code respects the caps listed below, and each cap binds as an error in a static analyzer. A [[callable,a callable]]_callable_ is a source-code construct that can be invoked, such as a function, method, or constructor.
+
[cols="<3,>1",options="header"]
|===
|Measure |Cap
|File length |500 lines
|Callable length |50 lines
|Parameters per callable |4
|Cyclomatic complexity per callable |8
|Control-structure nesting depth |3 levels
|Line length |120 characters
|===
. Where no tool for the programming language or platform measures a cap, a script of the xref:#governed-repository[governed repository] measures that cap, and the script is a xref:#check[check].
. Code that grows past a cap is refactored until every measured value meets the cap. A cap is never raised. A xref:#governed-repository[governed repository] may set caps stricter than the table and never sets looser ones.

[[types-and-null]]
=== Types and Null

. Where the programming language or platform provides a static type checker, the type checker is one of the xref:#check[checks].
. A xref:#callable[callable] doesn't return null and doesn't accept null where the programming language offers an optional or result type instead. A missing value is expressed as a typed value, such as an empty optional.
. A xref:#callable[callable] that can't do its job fails immediately with an error that says what went wrong. The callable doesn't fall back silently to a default.

[[explicitness]]
=== Explicitness

. Code takes the explicit form wherever the programming language offers an implicit shortcut. Types are written even where the type checker infers them. Return types are declared, visibility is declared, and conversions between types are spelled out.
. Every block is enclosed in braces where the programming language makes braces optional. A comparison uses the strict form where the programming language also offers a loose one. A conditional over a set of cases handles every case or declares an explicit default.

[[immutability-and-composition]]
=== Immutability and Composition

. Data is immutable. A field is assigned once, when its object is created, and a local variable is assigned once. Changed state is expressed as a new value, not as an overwrite of the old one. The only way to mutate is through a xref:#suppressions[suppression].
. A concrete type is closed to inheritance where the programming language can express the closure. A type stays open only where a dependency must subclass it at run time.
. New behavior is added by composing objects, not by inheriting. A type inherits only from a base that the programming language or a dependency requires - for example, the base error type.

[[dependency-structure]]
=== Dependency Structure

. A [[dependency-unit,a dependency unit]]_dependency unit_ is a named source-code division that can depend on another dependency unit, such as a module or package. The dependencies among the xref:#governed-repository[governed repository's] dependency units form a directed acyclic graph. A xref:#check[check] builds the graph from the code and fails on a cycle, naming the dependency units that lie on the cycle.
. A cycle is broken by moving the shared concept into a xref:#dependency-unit[dependency unit] that both sides depend on, or by inverting one direction behind an abstraction that the depended-on dependency unit declares. A cycle is never declared acceptable.

[[naming]]
=== Naming

. A name says plainly what the named thing is or does. One concept has one name everywhere in the xref:#governed-repository[governed repository].
. A type name is by default a noun of the domain the type models - for example, `Order`, `MaskedToken`, or `RetryPolicy`. An agent noun built on a verb, such as `Compiler` or `Scheduler`, fits where the role itself is the concept. Where a domain type can own the operation instead, the operation belongs to that type - for example, masking belongs to `MaskedToken`, not to a `TokenMasker`. The suffixes `Service`, `Manager`, `Handler`, `Provider`, and `Util` are banned, and a xref:#governed-repository[governed repository] may extend the ban.
. A name of one character is banned, except the placeholder that the programming language reserves for an unused value. For example, `maskedToken` says what `m` hides.
. A name consists of full words. An abbreviation appears only where it's more recognizable than the full form - for example, `id` or `URL`, not `usrCfg`.

[[banned-constructs]]
=== Banned Constructs

. A bare number in code is banned: a number appears only in the declaration of a named constant. The only exception is a short structural-value allowlist, such as 0 and 1, that the xref:#governed-repository[governed repository] declares.
. Dead code is banned: a xref:#check[check] fails on an unused file, an unused xref:#callable[callable], an unused parameter, an unused dependency, and an unused export outside the declared public interface of the xref:#governed-repository[governed repository].
. `TODO` and `FIXME` comments are banned.
. A call to an API that its own supplier marks deprecated in the released artifact is banned.
. A ban specific to one xref:#governed-repository[governed repository] becomes a xref:#check[check] when the check can verify it reliably, and it isn't restated in the xref:#instruction-file[instruction file].

[[suppressions]]
=== Suppressions

. A _suppression_ is a machine-readable exception that turns one named rule off at the narrowest scope its tool supports. The suppression is a source annotation where the tool supports one. A tool that has no stable source-annotation form may use a declared configuration entry or baseline record instead.
. Every suppression carries a concise justification in the source annotation, configuration, or baseline record that declares it.
. A xref:#check[check] fails on a suppression without a justification, on one broader than its tool requires, and on one that no longer suppresses anything.
. A [[suppression-ceiling,a suppression ceiling]]_suppression ceiling_ is a declared limit on the suppression count of a xref:#governed-repository[governed repository]. A xref:#check[check] fails when the count passes the suppression ceiling. Whoever adds a suppression writes its justification, so the justification never stops one from being added. The suppression ceiling stops one, because it makes the next suppression cost the removal of an existing one.
. The xref:#suppression-ceiling[suppression ceiling] is expressed against the size of the code rather than as a bare count, so it neither strangles a small xref:#governed-repository[governed repository] nor loosens as a large governed repository grows. A suppression ceiling of zero states that no suppression is permitted.
. Every run of the xref:#verification-command[verification command] reports the suppression count and the distance left to the xref:#suppression-ceiling[suppression ceiling], so the trend is readable before the suppression ceiling is reached.

[[typography]]
=== Typography

. The following characters are banned: the em dash, the en dash, typographic quotation marks, and the single-character ellipsis. The plain equivalents - the hyphen, the straight quotation mark, and three periods - stand in their place.
. The banned characters are absent from every commit message and from every tracked file the xref:#governed-repository[governed repository] doesn't exclude by xref:#file-role[file role]. A xref:#check[check] scans those files by code point and fails on the first finding.

[[dependencies]]
== Dependencies

. This section governs the licenses and vulnerabilities of third-party packages used by the xref:#governed-repository[governed repository] and the freshness of dependency, plugin, and parent versions.
. [[declared-coordinate,a declared coordinate]]A _declared coordinate_ is the identity and version of a dependency, plugin, or parent declared in a manifest of the xref:#governed-repository[governed repository] or an inherited manifest.
. [[resolved-set,the resolved set]]The _resolved set_ contains the packages identified by xref:#declared-coordinate[declared coordinates] and all packages they pull in.

[[dependency-licenses]]
=== Licenses

. Every package in the xref:#resolved-set[resolved set] carries a license that appears on a license allowlist the xref:#governed-repository[governed repository] declares. A xref:#check[check] reads the license of each such package and fails on a license outside the license allowlist.
. The license allowlist names license identifiers, not individual packages. A package whose license the xref:#check[check] can't resolve fails the check, like any package whose license lies outside the license allowlist.

[[dependency-vulnerabilities]]
=== Known Vulnerabilities

. A xref:#check[check] reads every package in the xref:#resolved-set[resolved set] against a public vulnerability database. It fails on any known vulnerability at or above the severity the xref:#governed-repository[governed repository] declares.
. The xref:#check[check] covers packages used by the product, tests, and build. Build tools run with build privileges, so their vulnerabilities are reachable by anyone who can change the xref:#governed-repository[governed repository].
. A finding is resolved by upgrading the package. If no upgrade exists, a declared vulnerability allowlist records the advisory. Each entry explains why the xref:#governed-repository[governed repository] can't reach the vulnerability and records its addition date.
. Every vulnerability-allowlist entry suppresses a finding. An entry that suppresses none fails the xref:#check[check].
. The vulnerability xref:#check[check] reads a public database, so its verdict can change while the xref:#governed-repository[governed repository] stays unchanged. The section xref:#check-qualities[] excludes the vulnerability check from determinism. An unreachable database fails the vulnerability check.

[[dependency-freshness]]
=== Freshness

. The freshness xref:#check[check] measures the major-version gap between a xref:#declared-coordinate[declared coordinate] and its latest stable release. A newer stable release is reported but doesn't fail the build on its own.
. An [[update-report,an update report]]_update report_ lists every newer stable release available for a xref:#declared-coordinate[declared coordinate]. Every build produces one for declared coordinates in the xref:#governed-repository[governed repository's] own and inherited manifests. For each coordinate, the report names the manifest that declares it.
. The [[freshness-bound,the freshness bound]]_freshness bound_ is fixed at a gap of two major versions. A xref:#governed-repository[governed repository] doesn't configure it. A xref:#declared-coordinate[declared coordinate] becomes noncompliant when its latest stable release is at least two major versions ahead. For example, version 71 fails when version 73 is available.
. The freshness xref:#check[check] compares every xref:#declared-coordinate[declared coordinate] in the xref:#update-report[update report] with its latest stable release. The check uses the numeric major version. For a version beginning with a four-digit year from 2000 through 2099, it treats the year as the major version. A stable release two or more years ahead therefore reaches the xref:#freshness-bound[freshness bound] and fails. The check excludes version schemes with neither a numeric major nor a leading year. It doesn't inspect transitive packages in the xref:#resolved-set[resolved set].
. Because the freshness xref:#check[check] reads the public package registry, the section xref:#check-qualities[] excludes it from determinism. A gap below the xref:#freshness-bound[freshness bound] passes, and a gap that reaches it fails. An unreachable registry also fails the check.

[[testing]]
== Testing

This section describes the state of the test suite and what it proves.

[[real-components-only]]
=== Real Components Only

. [[substitute-criterion,the substitute criterion]]A [[real-component,a real component]]_real component_ is a component that implements the behavior of the protocol it stands for. A [[substitute,a substitute]]_substitute_ is a component whose answers the test declares. The component's name decides nothing: an in-memory library component that implements a protocol is real, and a class inside the test tree whose answers a test sets is a substitute.
. A test uses no xref:#substitute[substitutes]. It runs against xref:#real-component[real components]: a real database, a real server on a local port, or a real temporary file.
. A service that exists only outside the machine is exercised through a local component that implements its protocol. The local component supplies the protocol's behavior on the machine that runs the test.
. A xref:#check[check] fails on the construction of a xref:#substitute[substitute] in test code. The check names the libraries and framework declarations of the programming language or platform that install a substitute in place of a xref:#real-component[real component]. The check binds xref:#substitute-criterion[] and not a name, so a local component stays available however its library is named.
. Test code passes the same xref:#check[static-analysis checks] as production code.

[[coverage]]
=== Coverage

. Line coverage and branch coverage are at least 80% in every measured file. A file with no branches satisfies the branch floor.
. An exclusion names something the coverage report measured. A xref:#check[check] fails on an exclusion that reaches nothing, because a pattern that matches no class excludes nothing and leaves the report reading exactly as it would have read without it.

[[determinism]]
=== Determinism

. A test produces the same verdict on every run.
. A test reaches no network beyond the machine it runs on. Every wait a test performs is bounded by a timeout sized so that its expiry signals a defect of the code, not the speed of the machine.
. A test reaches its verdict whatever order the test suite runs in.

[[test-integrity]]
=== Test Integrity

. A xref:#check[check] fails when test code selects one test or test group to run instead of the complete suite. It also fails when a test is commented out. A test is skipped only by a declared rule that names a platform condition, never by an annotation in the test itself.
. A test verifies one behavior and states that behavior in its name.
. A test asserts an observable outcome. A xref:#check[check] fails on a test that reaches no assertion, so a test that drives the code without judging what the code produced reports as missing rather than as passing.
. An assertion whose verdict doesn't depend on the code under test is banned, because no change to that code can make the assertion fail. A xref:#check[check] fails on an assertion whose operands are literals alone, such as an assertion that a constant is true.
. Coverage counts the lines a test ran, not the behaviors a test judged. The floors of the section xref:#coverage[] and the rules above therefore bind together, and neither one stands in for the other.
. A test fails when the behavior its name states is removed from the code under test. No xref:#check[automated check] verifies this rule reliably, so an xref:#instruction-file[instruction file] states it, and an inspection against the wording of that rule decides compliance.

[[version-control]]
== Version Control

This section describes the state of the commit history and of the continuous integration that guards the main branch.

[[commit-messages]]
=== Commit Messages

. Every commit message passes a xref:#check[check]. Its commit header has the form `type: subject` or `type(scope): subject`. The commit type is one of `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, or `test`.
. The commit subject holds 15 to 72 characters, ends without a period, and contains none of these words: `wip`, `tmp`, `temp`, `misc`, `stuff`, `asdf`, `fixup`.
. A change that touches more than 2 files or changes more than 50 lines carries a commit body that states why the change was made.
+
[source,text]
----
feat(obfuscation): mask bearer tokens in request headers

Provider tokens leaked into the proxy logs through the header dump.
Masking them in the header parser closes the leak for every consumer.
----
. No commit message attributes the change to an AI agent or to an AI agent session. No co-authorship trailer, sign-off address, session identifier, or generated-by signature that names an AI agent or the session that produced the change appears in any commit message. A xref:#check[check] scans each commit message for the known attribution markers and fails on a finding. Because no pattern can enumerate every AI agent, an xref:#instruction-file[instruction file] states the rule in prose as well, and an inspection against the wording of that rule decides a marker the check doesn't yet know.
. The xref:#check[commit-message checks] are deterministic per commit, so the xref:#verification-command[verification command] applies them not only to new commits but to every commit reachable from the head of the main branch, back to and including the first commit, and fails when any commit violates one. Every commit satisfied the checks when it was recorded, so the commit history stays compliant by construction, and a failure signals a commit that reached the branch without the required verification.

[[linear-history]]
=== Linear History

. The history is linear: no commit has more than one parent. A branch takes the work of another by a rebase or a cherry-pick.
. A xref:#check[check] walks the commit history, back to and including the first commit. A commit with more than one parent fails the check.
